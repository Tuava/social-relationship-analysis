# 社会关系分析平台设计文档

## 1. 文档状态

- 版本：0.2
- 状态：讨论稿
- 更新时间：2026-08-13
- 当前目标：先确定问题定义、数据边界和系统分层，再根据 QQ 空间接口细节确定实现方案。

## 2. 项目目标

构建一个以个体为中心的社会关系分析工具。QQ 空间、NapCat 和后续接入的其他接口都视为有价值的观测面，不预先划分主次。系统将来自不同平台的数据统一整理为可追溯的实体、事件和证据，再分析目标账号的关系网络及其随时间的变化。

这里的“关系”指数据中可以观察到的互动关系，不直接等同于现实中的友谊、亲密度、社会地位或心理特征。

## 3. 非目标

第一阶段不做以下事情：

- 绕过 QQ 空间、QQ群或账号的访问权限；
- 把网络指标直接解释成现实中的确定结论；
- 一开始就绑定某个前端框架或数据库集群；
- 把某一个平台当作完整的社会关系数据库；
- 把“可能是学校/爱好”的推断展示成未经证据支持的确定事实。

## 4. 数据源与观测面

数据源不按主次排序，而按“能观察到什么”来组织。不同来源中的同一个 QQ 号、群、内容和行为必须通过统一实体标识关联起来。

### 4.1 QQ 空间

QQ 空间重点提供以下对象和事件，具体以实际接口能力为准：

- 用户及其公开资料；
- 说说或动态；
- 点赞；
- 评论；
- 评论回复；
- 内容发布时间和互动时间；
- 可用于识别关系对象的用户标识。

QQ 空间数据的主要价值是提供个体长期表达和持续互动记录，从而支持关系强度、关系方向和关系变化分析。

### 4.2 NapCat

NapCat 重点提供以下对象和事件。根据 NapCat 4.18.18 API，后续可考虑使用：

- `get_login_info`：确认当前登录账号；
- `get_group_list`：获取当前账号可见的群；
- `get_group_member_list`：获取指定群的成员列表；
- `get_group_member_info`：获取指定群成员详情；
- `get_group_msg_history`：获取指定群的历史消息；
- WebSocket 事件：接收运行期间产生的实时群消息。

NapCat 主要覆盖群体场景、群成员结构和实时互动；QQ 空间主要覆盖内容表达及其互动。二者都只是部分观测，不能单独代表完整 QQ 好友关系或完整社会关系。

### 4.3 数据留存原则

在授权范围内，采集到的原始数据应尽量完整留存，而不是只保留聚合后的次数。至少包括：

- 原始聊天消息及其消息 ID、发送者、时间、群/会话上下文；
- 原始空间动态、评论、回复、点赞和访客记录；
- 用户头像、昵称、群名片、备注等资料的历史版本；
- 原始接口响应、采集时间、来源接口、分页游标和哈希；
- 下载媒体的元数据及来源引用，媒体文件是否落盘由存储策略决定。

“留存所有”必须受数据范围、授权状态、访问控制和本地加密约束。原始聊天不应默认展示给不具备权限的用户，也不应把 Token、Cookie 或原始个人数据提交到代码仓库。

## 5. 总体架构

```text
QQ 空间接口 ─┐
NapCat 接口 ─┼─ 数据源适配层 ─ 原始留存层 ─ 实体对齐层 ─ 关系事件库 ─ 分析引擎 ─ 查询 API ─ 可视化界面
其他接口 ────┘                                      │
                                                    └─ 证据与推断记录
```

### 5.1 数据源适配层

每个数据源使用独立适配器，负责：

- 认证和会话管理；
- 分页、增量和断点续采；
- 请求重试和限流；
- 原始响应保存；
- 将平台错误转换为统一错误；
- 输出标准化前的采集记录。

建议的模块边界：

```text
collectors/
├── qzone/
├── napcat/
└── common/
```

### 5.2 数据标准化层

平台字段不能直接进入分析逻辑。标准化层需要统一：

- 用户标识；
- 群、空间和内容标识；
- 时间格式和时区；
- 文本、图片和其他内容引用；
- 点赞、评论、回复、提及等行为类型；
- 数据来源和采集批次。

### 5.3 关系事件库

核心抽象是“关系事件”，而不是一条静态边：

```text
actor       发起行为的用户
target      行为指向的用户或内容
action      行为类型
occurred_at 行为发生时间
source      数据来源
context     发生场景，例如空间动态或群聊
evidence    能够回溯原始记录的引用
```

这样可以在未来重新调整权重或分析方法，而不需要重新请求平台数据。

### 5.4 实体对齐层

不同接口可能使用不同字段表达同一个人。实体对齐层负责把平台账号、群成员、空间作者、评论者、点赞者和访客关联到统一的 `person` 实体，同时保留每一次对齐的来源和置信度。

不能仅依靠昵称或头像判断同一人。优先级应为：平台唯一 QQ 号 > 明确的接口引用 > 经过审核的别名/资料关联 > 不自动合并的候选匹配。

### 5.5 AI 分析层

大模型是分析层的一个可替换组件，不是事实数据库，也不直接拥有数据库写权限。它通过“证据包”读取经过范围控制的数据，输出结构化的分析候选和证据引用。

```text
关系事件/消息
      ↓
证据筛选器 Evidence Builder
      ↓
脱敏、截断、来源标记、预算控制
      ↓
LLM Gateway / Model Provider
      ↓
结构化输出校验
      ↓
推断记录、摘要草稿或人工审核队列
```

AI 可以用于：

- 从消息和动态中提取主题、实体、兴趣候选和场景线索；
- 识别评论、回复、提及和引用的语义关系；
- 对关系事件进行摘要和解释；
- 对可能的学校、兴趣、活动场景生成带证据的候选推断；
- 辅助发现昵称、头像和账号之间的候选实体匹配。

AI 不可以直接：

- 修改原始记录、关系事实或用户身份；
- 在没有证据引用的情况下生成确定结论；
- 绕过权限读取数据；
- 把模型猜测写入 `persons`、`groups` 或 `contents` 的事实字段；
- 默认把完整聊天数据库发送给远程模型。

模型输出必须经过 JSON Schema 校验，且每条候选结论包含 `evidence_ids`、`confidence`、`model`、`prompt_version` 和 `review_status`。

## 6. 建议的数据模型

正式主库采用 PostgreSQL。项目需要同时保存关系事件、完整消息、资料历史、原始 JSON、AI 运行记录和证据索引，并支持全文检索、并发采集和后续扩展，SQLite 不适合作为长期主库。

大文本和结构化原始响应放在 PostgreSQL 的 `jsonb`/文本字段中；头像、图片、语音、视频和文件等二进制内容放在本地文件系统或 S3-compatible 对象存储中，数据库保存 SHA-256、对象路径、媒体类型、大小和来源。这样原始数据仍然完整可追溯，但不会让关系数据库承担大规模二进制存储。

## 7. 关系构建原则

不能把“同群”或“同一时间在线”直接当作强关系。第一版至少区分：

- `like`：点赞；
- `comment`：评论；
- `reply`：回复；
- `mention`：提及；
- `quote`：引用；
- `group_message`：群消息互动；
- `co_presence`：共现，只作为弱关系或辅助特征。

关系权重应由配置决定，并且保留各行为的原始计数。例如：

```text
edge_weight =
    like_count * like_weight
  + comment_count * comment_weight
  + reply_count * reply_weight
  + mention_count * mention_weight
```

权重不是事实结论，只是某种分析视角。界面必须能展示权重来源和时间范围。

## 8. 分析能力规划

### 第一阶段

- 用户、内容和关系事件浏览；
- 时间范围过滤；
- 点赞、评论、回复的方向图；
- 互动次数和活跃度统计；
- 关系证据回溯；
- JSON、CSV 和 HTML 导出。

### 第二阶段

- PageRank、度数、介数中心性；
- 社群发现；
- 关系强度随时间的变化；
- 个体中心网络；
- 不同数据源之间的关系合并；
- 采集任务的断点续传。

### 第三阶段

- 实时事件接入；
- 增量分析；
- 多账号或多数据源管理；
- 分析配置版本化；
- 更完整的前端工作台。

## 8A. 第一功能：目标账号一阶扩散图

### 8A.1 功能定义

输入一个目标 QQ 号和数据范围，系统从所有已接入且有授权的数据源中收集与该账号直接相关的原子，再扩散一层，形成可解释的个体中心图。

这里的“一阶扩散”不是无限爬取：每个节点和关系都必须记录发现路径、来源和时间窗口。例如：

```text
目标账号
├── 参与过的群
│   └── 群成员、群消息参与者、被回复者
├── 发布过的空间动态
│   └── 点赞者、评论者、回复者、访客
├── 目标账号的历史消息
│   └── 会话对象、被提及者、引用对象
└── 目标账号的资料版本
    └── 昵称、头像、群名片、公开资料变化
```

随后只对新发现的原子再展开一层，并设置节点类型、来源、时间范围和数量上限，避免一次任务无边界扩张。

### 8A.2 图中原子类型

- `person`：用户；
- `group`：QQ群或其他群体；
- `content`：空间动态、评论线程或其他内容；
- `message`：群聊或其他授权会话中的消息；
- `profile_snapshot`：头像、昵称、群名片等时间版本；
- `evidence`：支撑关系或推断的原始记录。

### 8A.3 图中关系类型

- `member_of`：用户属于群；
- `sent_message_in`：用户在会话中发言；
- `published`：用户发布内容；
- `liked`：用户点赞内容；
- `commented`：用户评论内容；
- `replied_to`：用户回复用户或消息；
- `visited`：用户访问空间；
- `mentioned`：内容提及用户；
- `quoted`：消息或内容引用另一条内容；
- `profile_seen_as`：某时间窗口内使用过某头像/昵称。

每条边需要携带 `source`、`first_seen_at`、`last_seen_at`、`event_count`、`evidence_ids` 和 `confidence`。

### 8A.4 目标账号的“加入过的群”

当前 NapCat 的 `get_group_list` 只能可靠表示当前账号可见的群列表，不能单独证明一个账号历史上加入过的全部群。历史加入关系需要来自：

- 采集期间保存的群列表快照；
- 历史群消息中的会话证据；
- 明确的入群/退群事件；
- 其他 QQ 空间或账号接口提供的历史记录。

因此界面要区分“当前可见群”“历史消息发现的群”和“有明确加入/退出证据的群”，不能把三者混成一个确定列表。

### 8A.5 第一版输出

- 目标账号的一阶关系图；
- 节点类型、来源和发现路径筛选；
- 时间范围筛选；
- 关系边的原始证据列表；
- 目标账号的群、消息、动态、点赞、评论、访客摘要；
- 头像和昵称时间线；
- 导出图数据和证据索引。

## 9. 采集和更新流程

### 首次采集

```text
确认授权和数据范围
→ 校验接口能力
→ 采集原始数据
→ 保存采集批次
→ 标准化实体和事件
→ 去重
→ 生成分析快照
```

### 增量采集

```text
读取上次游标
→ 请求新增数据
→ 保存原始响应
→ 按 payload_hash 去重
→ 写入新事件
→ 更新受影响关系
→ 记录新的游标和批次状态
```

必须支持失败重试、速率限制、任务取消和错误记录；不应依赖一次性全量抓取。

## 10. 技术栈定案

采用“Go 后端 + Vue/TypeScript 前端 + 可替换 AI Gateway”的单机优先架构。这个项目的主要难点在数据采集、实体对齐、证据留存和图分析，不在高并发，因此第一版不引入微服务和消息队列。

### 10.1 后端

```text
Go 1.23+
chi           HTTP 路由和中间件
sqlc          根据 SQL 生成类型安全的数据访问代码
PostgreSQL 16+ 正式主库
pgx           PostgreSQL 驱动和连接池
goose         数据库迁移
net/http      QQ 空间、NapCat 和 AI HTTP 客户端
coder/websocket NapCat WebSocket 事件接收
encoding/json 外部数据和模型输出解析
gonum/graph   基础图结构和图算法
```

Go 适合本项目的原因：

- goroutine 和 channel 适合同时处理多个采集任务、WebSocket 事件和写入队列；
- 静态类型适合维护用户、内容、消息、关系事件和证据之间的复杂契约；
- 编译后可以生成单个可执行文件，部署和分发简单；
- 标准库对 HTTP、JSON、并发、文件和加密支持完整；
- 长时间运行的采集服务比脚本型实现更容易控制生命周期和资源使用。

Go 的取舍：图算法和自然语言处理生态不如 Python 丰富。因此第一版只实现目标一阶扩散、遍历、关系聚合和必要的中心性指标；复杂 NLP 交给 AI Gateway。若以后出现确实需要的专业算法，再以独立服务接入，不把 Python 预先塞进主工程。

### 10.2 前端

```text
TypeScript
Vue 3 + Vite  本地分析工作台
Vuetify 3     表单、布局、表格、抽屉、时间线和主题系统
Pinia         全局状态和任务状态
Vue Router    页面和分析任务路由
Cytoscape.js  关系图和一阶扩散图
ECharts       时间线、活跃度和关系统计
ofetch        API 请求封装
```

选择 Vue 3 + Vite + Vuetify 3 构建本地分析工作台。Vuetify 负责应用壳、导航、筛选器、数据表、详情抽屉、时间线、对话框和主题，不负责专业关系图；关系图使用 Cytoscape.js，统计图使用 ECharts。后续如果需要桌面应用，可以在不改后端契约的情况下再套 Tauri。

Vuetify MCP 只作为开发辅助工具，用于查询 Vuetify 组件 API、属性、示例和设计规范，不参与生产运行时。托管 MCP 地址为 `https://mcp.vuetifyjs.com/mcp`；需要本地运行时可使用 `npx -y @vuetify/mcp`。

### 10.3 AI Gateway

AI 接入统一走内部接口，不在业务代码中直接调用某个厂商 SDK：

```text
ai/
├── gateway.go       统一调用入口
├── providers.go     OpenAI-compatible、云厂商、本地模型适配器
├── schemas.go       结构化输入输出模型
├── prompts/         版本化提示词
└── evidence.go      证据包生成和脱敏
```

第一版支持三类 Provider：

1. OpenAI-compatible HTTP 接口，便于接入不同服务商；
2. 本地模型接口，适合敏感原始聊天不出本机的场景；
3. 可选云模型接口，必须显式配置并记录数据发送范围。

AI Gateway 需要统一处理：超时、重试、Token 预算、模型版本、结构化输出、调用日志和失败降级。默认只传摘要或证据片段，不把数据库连接、Cookie、Token 和无关用户数据交给模型。

```text
├── data/              本地对象存储和导出数据，不提交到仓库
└── .env.example
```

### 10.5 第一版运行方式

第一版使用一个 Go 进程、一个 Vue 开发服务器和一个 PostgreSQL 实例：

```text
Go API   http://127.0.0.1:8000
Vue      http://127.0.0.1:5173
PostgreSQL 127.0.0.1:5432
Object storage data/objects/
```

采集任务先使用 Go 的 context、goroutine 和受控 channel 执行，并提供独立 CLI 子命令。只有当任务规模、并发或实时性证明需要时，才引入 Redis、NATS 或消息队列。

### 10.6 数据库决策

| 方案 | 决策 | 原因 |
|---|---|---|
| PostgreSQL | 采用 | JSONB、全文检索、并发、事务、分区表和后续 pgvector 都适合本项目 |
| SQLite | 不作为正式主库 | 适合测试或极简演示，但不适合作为持续采集和多任务分析的长期数据底座 |
| Neo4j | 第一版不采用 | 图遍历方便，但原始证据、版本、来源和时间窗口仍需要关系型存储；当前会增加同步和部署复杂度 |
| DuckDB | 作为可选分析工具 | 适合离线报表和导出分析，不作为在线事实库 |
| 对象存储 | 采用 | 保存头像、图片、语音、视频和文件等二进制；PostgreSQL 保存元数据和证据引用 |

PostgreSQL 第一版启用：

- `jsonb`：原始接口响应和消息段结构；
- `GIN`：JSON、文本和全文检索索引；
- `pg_trgm`：昵称、群名片和内容的模糊检索；
- 时间分区：数据量达到阈值后对消息和事件按月份分区；
- `pgvector`：只有在需要语义搜索或 embedding 关系分析时再启用，不作为第一天的硬依赖。

## 11. 待确认问题

在开始编码前，需要根据你提供的 QQ 空间接口逐项确认：

1. 能获取哪些对象：用户、说说、评论、点赞、回复、访客、好友或其他关系。
2. 是否需要登录态，登录态的生命周期和刷新方式是什么。
3. 是否支持按时间、游标或内容 ID 增量获取。
4. 点赞、评论和回复是否包含明确的用户标识和时间。
5. 回复是否能可靠识别被回复对象。
6. 是否存在接口频率限制、分页上限和错误码。
7. 数据是否只限于账号本人可见内容。
8. 预期的分析范围、时间跨度和数据量。
9. 第一版更重视关系图、统计报表，还是关系证据检索。
10. “历史加入的群”由哪些接口或历史快照证明，能否接受“发现过的群”和“明确加入过的群”分开呈现。
11. 聊天原文、图片、文件和语音是否全部落盘，还是原文落盘、媒体保留引用。
12. 头像和昵称需要保存完整历史，还是保存每次采集到的版本快照。
13. 学校、爱好等推断哪些属性允许展示，是否需要人工确认后才显示。
14. AI 使用本地模型、远程模型，还是两者并存；哪些数据允许发送到远程服务。
15. 是否需要保留 AI 的输入证据包和完整输出，以便审计和复现。

## 12. 设计决策记录

### D-001：所有数据源都是观测面，不预先区分主次

理由：QQ 空间、NapCat 和后续接口观察的是同一社会网络的不同切面。数据价值取决于能否与其他实体和事件关联，而不是来源名称。系统在采集层完整留存，在分析层按证据和关联质量使用。

### D-002：Go 作为后端实现语言

理由：Go 能覆盖 HTTP、WebSocket、并发采集、结构化数据处理和本地部署，同时避免 Python 运行时与依赖管理成为项目负担。前端仍使用 TypeScript，AI 通过 HTTP Gateway 解耦。

### D-003：先做单机模块化版本

理由：当前最大不确定性是 QQ 空间接口的实际返回结构和权限边界。先降低部署复杂度，把精力放在数据契约、事件模型和分析有效性上。

### D-004：原始记录与关系事件分离

理由：分析权重和算法会迭代，保留原始证据可以重复处理并解释结果。

### D-005：第一功能采用有限的一阶扩散

理由：先验证实体对齐、事件留存和证据链是否可靠，再扩大深度。无边界扩散会快速扩大数据范围，也会让结果难以解释和审计。

### D-006：AI 通过 Gateway 接入

理由：模型供应商、部署位置和模型版本会变化。统一 Gateway 可以隔离厂商差异、控制敏感数据范围，并保存提示词版本、证据包和结构化输出。

### D-007：事实库与 AI 推断隔离

理由：模型输出可能错误或过度推断。事实数据只能来自已留存的原始记录和标准化事件；AI 结果必须作为带证据、置信度和审核状态的独立记录。
